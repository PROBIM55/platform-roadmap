# Сценарии

Во всех сценариях:

- `BASE` — `https://bimplatforma.ru`; в каждом запросе заголовок `Authorization: Bearer $PLATFORM_API_KEY`;
- `PLAN` — `BASE/api/platform/projects/{projectId}/network-federation` (корень маршрутов сводного плана);
- идентификаторы берутся из ответов сервера, а не придумываются;
- после первого отказа по проекту (403, 404) программа останавливается (см. [соглашения](02_соглашения.md)).

Готовые примеры на Python — в папке [examples/python](examples/python).

## 1. Проверить ключ и прочитать план

**Шаг 1. Чей ключ.**

```
GET BASE/api/platform/network-federation/me
```

Ответ показывает владельца, режим, срок и проекты ключа с вашей ролью в каждом. Идентификатор нужного проекта — отсюда.

**Шаг 2. План проекта.**

```
GET PLAN
```

Нужные части ответа:

```json
{
  "ok": true,
  "document": {
    "version": 42,
    "disciplines": [ { "id": "discipline_…", "name": "Водоснабжение" } ],
    "sections": [
      {
        "id": "section_…", "disciplineId": "discipline_…", "name": "План сетей В1",
        "acceptedCadVersionId": "cadver_…",
        "cadVersions": [
          { "id": "cadver_…", "number": 3, "fileName": "plan_v1.dwg", "sourceUnit": "mm",
            "status": "accepted", "sha256": "…", "createdAtUtc": "…" }
        ],
        "modelSources": []
      }
    ]
  },
  "permissions": { "canAdminister": false, "canWrite": true, "canCoordinate": false, "disciplineIds": ["discipline_…"] }
}
```

**Как найти файл по имени.** Найдите раздел в `document.disciplines` по `name`, затем в `document.sections` — файл с этим `disciplineId` и нужным `name`. Имена файлов в разделе уникальны без учёта регистра, поэтому сравнивайте без учёта регистра. Актуальная версия файла — та, чей `id` равен `acceptedCadVersionId`; если принятой версии ещё нет, `acceptedCadVersionId` пуст.

Что вы видите, зависит от роли: координатор и администратор — все версии, остальные — принятые, а «Загрузка» ещё и любые версии своих разделов. Сохраните `document.version` — он нужен для решений в сценарии 5.

## 2. Скачать оригинал версии и архив раздела

**Оригинал версии.**

```
GET PLAN/sections/{sectionId}/cad-versions/{versionId}/original
```

Ответ — файл (DWG или DXF как загружен), имя в `Content-Disposition`. Поддерживаются частичные запросы (`Range`). Если версия вам по роли не видна — 403 `NETWORK_SOURCE_ACCESS_DENIED`; если версии или файла нет — 404 без тела. Модель IFC:

```
GET PLAN/sections/{sectionId}/models/{modelId}/versions/{versionId}/original
```

**Архив раздела** (оригиналы актуальных версий):

```
GET PLAN/archive?disciplineId={disciplineId}
```

Без `disciplineId` — архив всех разделов. Ответ — ZIP (`application/zip`) потоком: внутри папки по разделам. Ошибки (например, раздела нет) приходят обычным JSON до начала потока. Сохраняйте ответ в файл по частям и проверьте результат как ZIP: оборванный поток даёт неполный архив. Версии, которых вы по роли не видите, в архив не попадают.

## 3. Загрузить новую версию чертежа

Нужна роль «Загрузка» (с назначенным разделом), «Координатор» или «Администратор» и ключ в режиме «Полный — по роли».

### 3.1. В существующий файл

**Шаг 1. Лимиты (необязательно).**

```
GET PLAN/uploads/limits
→ { "ok": true, "maxSourceBytes": 67108864, "maxChunkBytes": 8388608 }
```

**Шаг 2. Открыть сессию.** Нужны размер файла и его SHA-256 (64 шестнадцатеричных знака, строчными):

```
POST PLAN/uploads
{ "disciplineId": "discipline_…", "fileName": "plan_v2.dwg", "declaredBytes": 20000000, "sha256": "…" }
→ { "ok": true, "session": { "sessionId": "upload_…", "receivedBytes": 0, "status": "uploading", … } }
```

Принимаются только файлы `.dwg` и `.dxf`. Сессию видит только тот, кто её открыл.

**Шаг 3. Куски по порядку.** Каждый кусок — до 8 МиБ (8 388 608 байт):

```
PUT PLAN/uploads/{sessionId}/content
Content-Type: application/octet-stream
Content-Range: bytes 0-8388607/20000000

<двоичные данные куска>
→ { "ok": true, "session": { "receivedBytes": 8388608, … } }
```

Следующий кусок — `bytes 8388608-16777215/20000000`, последний — `bytes 16777216-19999999/20000000`. Число после косой черты всегда равно `declaredBytes`. Куски идут строго с позиции `receivedBytes`. После обрыва прочитайте `GET PLAN/uploads/{sessionId}` и продолжите с `receivedBytes`; повтор уже принятого куска безопасен.

**Шаг 4. Завершить.**

```
POST PLAN/uploads/{sessionId}/complete
→ 202 (заголовок Location указывает на чтение импорта) { "ok": true, "item": { "importId": "…", "status": "queued", "detectedSourceUnit": null, "sourceUnitDetection": "unknown", … } }
```

Сервер сверил размер и SHA-256 и поставил файл в очередь разбора. При несовпадении суммы — 422 `CAD_UPLOAD_SHA256_MISMATCH` (сессия потеряна, загрузите заново).

**Шаг 5. Дождаться окончания импорта.** Опрашивайте не чаще раза в 2–3 секунды:

```
GET BASE/api/platform/projects/{projectId}/cad-imports/{importId}
→ { "ok": true, "item": { "status": "running", "phase": "normalizing", … } }
```

`status`: `queued`, `running`, затем `succeeded` или `failed` (причина в `error` и `diagnostics`). Опрос прекращайте при `succeeded`, `failed` или `cancelled`. Из ответа берите `detectedSourceUnit` («m» или «mm») при `sourceUnitDetection: "detected"`.

**Шаг 6. Зарегистрировать версию.**

```
POST PLAN/sections/{sectionId}/cad-versions
{ "importId": "…", "sourceUnit": "mm", "note": "Добавлены сети В1 на участке 2", "label": "Рабочая" }
→ { "ok": true, "cadVersion": { "id": "cadver_…", "number": 4, "status": "submitted", … } }
```

`sourceUnit` — «m» или «mm»: единицы, в которых начерчен файл (при сомнении спросите автора, значение подсказки `detectedSourceUnit` не заменяет вашего знания). `note` — «что изменилось», до 1000 знаков, видна рецензенту. Статус сразу после регистрации: у «Загрузки» — `submitted` («на проверке»); у координатора и администратора — `accepted`, если показ уже готов, иначе `submitted` с автопринятием, когда показ подготовится. Если в файле уже есть версия с той же SHA-256 и теми же единицами, сервер возвращает её — в любом статусе, в том числе «возвращена»: загрузка неизменённого файла после возврата на проверку ничего не отправит, исправьте чертёж. После обрыва ответа повтор этого запроса безопасен.

**Шаг 7 (необязательно). Дождаться подготовки показа.**

```
GET PLAN/processing?sectionId={sectionId}
→ { "ok": true, "active": true, "retryAfterMs": 2500, "items": [ { "versionId": "cadver_…", "state": "processing", … } ] }
```

Опрашивайте с паузой `retryAfterMs` (сервер называет 2500 или 10000 миллисекунд), пока у вашей версии `state` не станет `ready` (или `failed`). Если подготовка остановилась, её можно повторить: `POST PLAN/sections/{sectionId}/cad-versions/{versionId}/processing/retry`.

### 3.2. Новый файл

Если файла с таким именем в разделе нет, сначала заведите его, затем действуйте как в п. 3.1:

```
POST PLAN/sections
{ "disciplineId": "discipline_…", "name": "План сетей В1" }
→ { "ok": true, "section": { "id": "section_…", … } }
```

Если такой файл уже есть, придёт 409 `NETWORK_SECTION_NAME_DUPLICATE` — перечитайте план и загружайте в существующий. Если загрузка в сессии шла в раздел, отличный от раздела файла, регистрация получит 403 `NETWORK_CAD_IMPORT_DISCIPLINE_MISMATCH`.

## 4. Загрузить модель IFC

Модель — одним запросом, без сессии и кусков. Сначала заведите модель в файле, затем загрузите версию.

```
POST PLAN/sections/{sectionId}/models
{ "name": "Модель сетей В1", "format": "ifc" }
→ { "ok": true, "modelSource": { "id": "model_…", … } }

POST PLAN/sections/{sectionId}/models/{modelId}/versions?fileName=net_v1.ifc&sourceUnit=mm&note=Первая%20версия
Content-Type: application/octet-stream

<содержимое файла .ifc>
→ { "ok": true, "modelVersion": { "id": "ifcver_…", "number": 1, "status": "submitted", … } }
```

Предел — 512 МиБ. Значения в адресе кодируйте (`fileName`, `note`). Сервер проверяет заголовок STEP и конец файла, но геометрию не разбирает. У «Загрузки» версия идёт «на проверку», у координатора и администратора принимается сразу. Версия с той же SHA-256 и теми же единицами возвращается как есть, в любом статусе.

## 5. Проверка версий координатором

Нужна роль «Координатор» или «Администратор», режим ключа «Полный — по роли».

**Шаг 1. Найти версии на проверке.** В ответе `GET PLAN` — версии со `status: "submitted"` и `superseded: false` (если `superseded: true`, есть более новая версия, эту принять нельзя). Автор — `createdByUserId`, пояснение — `note`. Сохраните `document.version`.

**Шаг 2. Принять.** Принимается только последняя версия на проверке и только при готовом показе (`processing`: `state: "ready"`):

```
POST PLAN/sections/{sectionId}/cad-versions/{versionId}/accept
{ "expectedVersion": 42 }
→ { "ok": true, "cadVersion": { "status": "accepted", … } }
```

- 409 `NETWORK_CAD_VERSION_NOT_READY` — показ ещё готовится, подождите и повторите;
- 409 `NETWORK_CAD_VERSION_SUPERSEDED` — появилась более новая версия;
- 409 `NETWORK_FEDERATION_DOCUMENT_CONFLICT` — документ изменился, перечитайте план.

**Шаг 3. Вернуть с причиной.**

```
POST PLAN/sections/{sectionId}/cad-versions/{versionId}/return
{ "reason": "Не совпадают отметки на участке 2", "expectedVersion": 42 }
→ { "ok": true, "cadVersion": { "status": "returned", "returnReason": "…", … } }
```

Причина обязательна (1–1000 знаков). Автор видит её и загружает исправленную версию — возвращённую версию повторно не отправляют.

**Шаг 4. Сделать прежнюю версию актуальной.** Тем же `accept` над уже принятой, но не текущей версией (`status: "accepted"`, `id` не равен `acceptedCadVersionId` раздела): прежняя версия возвращается в актуальные со своим закреплённым размещением.

Для моделей IFC — те же действия: `…/models/{modelId}/versions/{versionId}/accept` и `…/return`.

## 6. Участники и права

Нужна роль «Координатор» или «Администратор». Координатор выдаёт и снимает только «Просмотр» и «Загрузку»; администратор — все четыре роли. «Координатор» и «Администратор» выдаются только сотрудникам компании проекта.

**Список участников и допустимые роли:**

```
GET BASE/api/platform/projects/{projectId}/modules/federated-networks/grants
→ { "actor": { "role": "coordinator", "assignableRoles": ["viewer", "uploader"] },
    "items": [ { "userId": "…", "username": "ivanov", "displayName": "Иванов И. И.",
                 "role": "uploader", "disciplineIds": ["discipline_…"], "editable": true, "removable": true } ] }
```

**Найти, кого добавить:** `GET …/grants/candidates?q=ивано` — сотрудники компании и известные гости, ещё не участники (до 50).

**Выдать доступ** существующей учётной записи (учётные записи этим не создаются):

```
POST …/grants
{ "username": "ivanov", "role": "uploader", "disciplineIds": ["discipline_…"] }
→ { "ok": true, "item": { "userId": "…", "role": "uploader", … } }
```

Для роли `uploader` нужен хотя бы один раздел. `viewer`, `coordinator`, `admin` разделов не требуют.

**Сменить роль или разделы:** `PUT …/grants/{userId}` с телом `{ "role": …, "disciplineIds": […] }`. **Убрать участника:** `DELETE …/grants/{userId}`.

**Пригласить нового человека** (гостя из другой организации) — приглашением; он получит ссылку и сам создаст учётную запись:

```
POST PLAN/invitations
{ "inviteeLabel": "Петров П. П., ООО «Пример»", "role": "editor", "disciplineIds": ["discipline_…"], "accessDays": 90 }
→ { "ok": true, "invitation": { "id": "…", "status": "pending", … }, "link": "/invite/…#…" }   // ссылка относительная: допишите базовый адрес
```

Роль приглашения — `viewer` («Просмотр») или `editor` («Загрузка», с разделами); координатором приглашение не делает. Ссылка с секретом возвращается один раз; передайте её человеку и не храните в журналах. Отозвать: `DELETE PLAN/invitations/{invitationId}`. Гости работают в интерфейсе и ключей не получают.

## 7. Обсуждения

Обсуждения видят и ведут участники в пределах версий, которые им видны.

**Список и счётчики:**

```
GET PLAN/discussions?status=open,in_progress&limit=50
GET PLAN/discussions/summary
```

**Завести обсуждение** (замечание). Обязательны привязка и хотя бы одно из двух — заголовок или текст; привязка (`anchor`): к элементу чертежа (`element`), элементу модели (`model-element`), области (`area`) или точке (`point`); у точки и области файла в привязке нет — это координаты `[x, y]` в миллиметрах:

```
POST PLAN/discussions
{ "title": "Пересечение с кабельной линией", "text": "Проверить отметку лотка на участке 2.",
  "anchor": { "kind": "point", "pointMm": [152000, 84000] },
  "priority": "high", "dueDate": "2026-12-01", "clientRequestId": "sync-2026-11-09-001" }
→ { "ok": true, "discussion": { "id": "…", "rowVersion": 1, … }, "message": { "id": "…", … } }
```

Повтор с тем же `clientRequestId` вернёт уже созданное обсуждение.

**Ответить:** `POST PLAN/discussions/{discussionId}/messages` с телом `{ "text": "Исправлено в версии 4" }`.

**Сменить статус** (`open`, `in_progress`, `review`, `resolved`) — с `rowVersion` из последнего ответа:

```
PATCH PLAN/discussions/{discussionId}
{ "status": "resolved", "rowVersion": 3 }
```

409 `NETWORK_DISCUSSION_ROW_VERSION_CONFLICT` — обсуждение уже изменили: перечитайте (`GET PLAN/discussions/{discussionId}`) и повторите.

**Что нового:** `GET PLAN/discussions/changes?after={cursor}` возвращает изменения после курсора; первый запрос без `after` возвращает текущий курсор.

## 8. Виды

Вид — сохранённая точка обзора (камера, при желании и показ). Личные виды ведёт любой участник, общие — участники с правом записи и координаторы.

```
GET PLAN/viewpoints
POST PLAN/viewpoints
{ "name": "Узел 2", "shared": false,
  "camera": { "centerMm": [152000, 84000], "widthMm": 12000, "heightMm": 8000 } }
→ { "ok": true, "viewpoint": { "id": "viewpoint_…", "rowVersion": 1, … } }
```

Изменить вид целиком — `PUT PLAN/viewpoints/{viewpointId}` (обязательны `name`, `shared`, `camera`, `rowVersion`); сделать общим или личным — `PATCH` с `{ "shared": true, "rowVersion": … }`; удалить — `DELETE PLAN/viewpoints/{viewpointId}?rowVersion=…`. Начальный вид сводной картины задаёт координатор: `PUT PLAN/viewpoints/{viewpointId}/home`; начальным может быть только общий вид без снимка. Конфигурации показа — маршруты `display-configurations` (см. [справочник](reference.md), группа «виды»).

## 9. Настроить порядок прорисовки в проекте

Нужен ключ «Полный — по роли» с правами координатора или администратора. Сначала прочитайте `GET PLAN`. В `document.disciplines` возьмите идентификаторы разделов, а в `document.sections` — идентификаторы чертежей. У чертежей из одного раздела значение `disciplineId` одинаковое.

Сохраните порядок разделов сверху вниз. Подоснова на плане остаётся снизу.

```
PUT PLAN/disciplines/order
{ "disciplineIds": ["discipline_a", "discipline_b"], "expectedVersion": 42 }
→ { "ok": true, "disciplineOrder": ["discipline_a", "discipline_b"], "version": 43 }
```

Затем сохраните порядок чертежей внутри нужного раздела. Передайте версию, которую вернул предыдущий запрос.

```
PUT PLAN/disciplines/discipline_a/drawing-order
{ "sectionIds": ["section_b", "section_a"], "expectedVersion": 43 }
→ { "ok": true, "drawingOrder": ["section_b", "section_a"], "version": 44 }
```

Это две отдельные записи. Если вторая получила `409` из-за конфликта версии, первая уже сохранена. Перечитайте план, сверив чужие изменения, и повторите только нужную запись с актуальным `expectedVersion`. При `428` добавьте пропущенную версию документа. Пустой список снимает сохранённый порядок на соответствующем уровне. Если в запросе есть только часть разделов или чертежей, пропущенные действующие позиции из прежнего порядка дописываются в конец.

Для проверки прочитайте `GET PLAN` заново и сравните `document.disciplineOrder` и `document.disciplines[].drawingOrder` выбранного раздела с порядком из ответов на запись. Сохранённый вид может содержать свои отличия от настроек проекта. См. [порядок разделов](reference.md#discipline-order) и [порядок чертежей](reference.md#discipline-drawing-order).

## 10. Черновик трасс и решения инженера

Черновик связан с точной версией чертежа и её размещением. Чтение доступно участникам, которым видна версия. Выделение и изменение решений требуют ключ «Полный — по роли» и право записи в соответствующий раздел.

Прочитайте сохранённый результат. Ответ содержит `draft` и `placementCurrent`, признак `ok` в этой форме ответа отсутствует.

```
GET PLAN/sections/{sectionId}/cad-versions/{versionId}/routes
→ { "draft": null, "placementCurrent": false }
```

Для выделения возьмите `document.version` из плана и идентификатор текущего размещения из маршрута `…/cad-versions/{versionId}/placements`. В его `items` выберите размещение с максимальным `number`. Если явных размещений ещё нет, список содержит исходное размещение `unit:{versionId}:{sourceUnit}` с номером 0. Передайте точные имена нужных слоёв, от 1 до 64 уникальных значений. Сервер читает геометрию исходного чертежа.

```
POST PLAN/sections/{sectionId}/cad-versions/{versionId}/routes
{ "placementId": "placement_…", "layers": ["Кабель_проект"], "expectedDocumentVersion": 42 }
→ { "id": "routes_…", "revision": 1, "report": { … }, "worldSegments": [ … ], "decisions": [], … }
```

POST возвращает сам черновик. В `report` координаты находятся в системе чертежа `drawing-wcs-mm`, в `worldSegments` — в миллиметрах проекта. Идентификаторы кандидатов берут из `report.candidates[].id`. Повтор с актуальным `expectedDocumentVersion`, теми же слоями, размещением и алгоритмом возвращает сохранённый черновик вместе с решениями инженера. Изменившийся алгоритм создаёт новый черновик, прежний сохраняется в истории.

Сохраните решение по кандидату, передав `revision` черновика.

```
PUT PLAN/route-drafts/{draftId}/candidates/{candidateId}
{ "status": "confirmed", "expectedRevision": 1 }
→ { "id": "routes_…", "revision": 2, "decisions": [ … ], … }
```

Допустимы `candidate`, `confirmed` и `excluded`. Ответ содержит обновлённый черновик. Повтор с прежней ревизией возвращает 409 `NETWORK_ROUTE_REVISION_CONFLICT`. Для устаревшего размещения сервер возвращает `NETWORK_ROUTE_PLACEMENT_CHANGED`, для заменённого черновика — `NETWORK_ROUTE_DRAFT_SUPERSEDED`. После изменения перечитайте черновик и план перед следующей записью. Коды ошибок reader и полный состав запросов приведены в группе «трассы» справочника.
